## 最近版本（详细）

- **v0.35.0**（2026-11-06）：**对齐 DSH 0.2.2-rc.1（当时 npm `latest`）的契约审计与两批落地**。先说结论：17 个工具、5 个宿主挂点（`tools` / `systemPrompt.section` / `commands` / `skills` / `webServer`）、6 个客户端座位**一个都没有被破坏**——`ToolDefinition`、`ToolOutputDefinition`、`json-schema.js`（出口校验器）、`dsh-commands`、`dsh-skill` 两版**字节相同**，座位表 103 → 109 **零删除**。所以这一版没有"修 bug"，全是"跟上前进 + 用上新能力"。
- **A：契约与元数据校准**。① `engines.dsh` 从 `>=0.2.1-rc.3` 改成 `>=0.2.1-rc.3 <0.3.0`——0.2.2 的 `dsh-app-boot` 会**真校验**它（`engines.dsh` 一旦存在，`peerDependencies` 就被完全忽略），没有上界等于对未来任何破坏版都声明兼容；下限**故意不抬到 0.2.2**：图标/右键菜单都是可选座位，老宿主上静默跳过、别的功能一切照旧。② 插件卡展示元数据补齐：`locale/{zh,en}.json` 只放 `meta.title`/`meta.description`（插件管理页在不激活插件的前提下读它），包根 `icon.svg` 走 `exports["./icon"]`；⚠️ 两样都必须同时在 `exports` 里开出来才生效（宿主用 Node ESM 解析器读，没导出就静默当"没有"）。③ 设置页导航拿到自己的图标：新座位 `settings.section.icon`（0.2.2 才有，`{id, order}` + `{size, active}`；与 `settings.section` **同一个 id**，宿主按 `only: row.id` 精确匹配、卸载即回落默认齿轮）——为此把 id/order 抽成 `SETTINGS_SECTION_ID` / `SETTINGS_SECTION_ORDER` 常量，改一个忘一个会静默失效。
- **B：会话右键菜单「绑定本会话知识库」**（此前只能靠输入框左侧那个下拉）。用 0.2.2 的 `contextMenus` 服务注册一个 `target: 'session'` 的 provider（`resolve` 返回父项 + 可见库子项 + 「跟随默认库」），**不是**占用 `contextMenu.content` 的 key——那个座位的 key 是 target.kind，占 `'session'` 会**顶掉工作区自己的菜单内容**（`replaceRisk: shadows-shipped-ui`）。三条硬约束：解析器**全程同步**（宿主对 Promise 有 1000 ms 竞速预算，超时它会自己弹失败 toast）、可见库 ≤1 时返回 `[]`（单库安装没有"绑定"可言）、以及 `contextMenus` **只能 `ctx.get()` 可选读、绝不能进 `dsh.client.inject`**（进去就等于"没有该服务的宿主上整个插件不加载"）。切库动作抽成 `client/session-wiki.ts` 一份实现，与 composer 选择器共用（选择器那 30 行内联 POST 一并删掉）。
- **顺手修掉的两处真问题**：① `verify-dsh-contract.mjs` 的工具视图切片用 `'] as const'` 当右界，而真实声明是 `: readonly string[] = [`——该子串不存在，`indexOf` 返回 **-1**，切片一路吃到文件尾（当前计数正确纯属巧合）；② 采集器只认 `name: '…'` 字面量，而 `sidebar.right.tab.document` 写在 `tid-parse.ts` 的常量里跨文件传递 ⇒ **v0.33.1 出事的那个 keyed 子槽从来没被守门覆盖过**。现在改成两段式（先建"值带点的字符串常量"表、按目录聚合，再解析 `name: <字面量|常量>`），并加一条**点名断言**——因为总数下限抓不住它：加完新座位是 8 个，常量解析失效会掉回 7，下限 7 照样绿（实测）。

- **v0.34.1**（2026-11-06）：**修 `tiddlywiki_search` 的「纯标签筛选」**（issue #1，用户实测报告）。
- **症状**：只传 `tags` / `tag`、不传 `query` 时**三层坏**，一层修完才露出下一层 —— ① `Cannot read properties of undefined (reading 'split')`；② 崩溃修掉后**恒返回 0 条**（标签过滤等于没生效）；③ 再修报 `tool "tiddlywiki_search" returned invalid output: value is not lossless JSON`。带 `query` 时一切正常，所以「按标签列出」这条日常用法一直没被任何用例走过。
- **三处根因**：① `TiddlyWikiClient.search()` 签名写死 `query: string` 且首行裸调 `query.split(…)`，而工具 schema 里 `query` 本就是可选的（`snippetAround` 同源，正文 > 160 字时同样炸）；② 空查询的短路 `if (terms.length === 0) return { items: [], total: 0 }` 写在 `wantedTags` 过滤**之前** ⇒ 标签判断永远执行不到；③ 回执里 `query: args.query` 把 `undefined` 回给宿主，DSH 的 lossless-JSON 校验因此判整次调用 invalid output。
- **修法**（原则：空 query 仍不匹配任何东西，但**有其它过滤条件时不短路**）：`search(query: string | undefined)` + `(query ?? '')`；短路条件收窄成「terms 为空**且** tags/since/type/field 都没有」；工具层先把 `args.query ?? ''` 归一，回执与 `snippetAround` 都用归一后的值；回执渲染在无关键词时改写成「按条件列出（按修改时间倒序）」，不再出现空的「搜索「」」。
- **守门**：`scripts/verify-tools.mjs` 新增一组 E2E（`tags` / 单值 `tag` / 多标签 AND / `tags`+`field:value` / `type`+`tag` / 长正文摘要 / 回执可 JSON 无损往返 / 渲染不含「搜索「」」），并把旧的「空白 query + tag 必须 0 条」断言改判成「**光有空查询**才 0 条」。反向验证：把归一去掉 ⇒ 无损往返断言 + schema 反查（`query 应为 string，实际 undefined`）双双变红；把短路条件还原 ⇒ 新用例与旧的多词 AND 用例变红。

- **v0.33.4**（2026-10-26）：**四路只读审计（host / 工具与数据路径 / 客户端 / 死代码）后的修复版**。

- **v0.33.3**（2026-10-26）：**`.tid` 预览的第一眼改成看内容，而不是看元数据**。
v0.33.2 修好注册之后，预览能出图了，但顶部把**所有**字段原样铺开：`created`/`modified` 是 17 位 UTC 戳（`20260920070533227`），`revision`/`workspace`/`ws/<项目>`/`agent-written` 这类机械字段也一字不落地占版面 —— 打开一个笔记，前两屏全是元数据。
现在新增纯函数 `summarizeTid()`（`src/client/tid-parse.ts`）：单列 `title` / `tags` / 时间，时间戳按 `YYYY-MM-DD HH:mm` 格式化（不是 17 位数字就**原样返回**，不装作看懂了）；`ws/*` 与 `agent-written` 不再占标签位，但会在「另外 N 个字段」那行留一个 `tags(hidden)=…` 的影子 —— **折叠不等于丢弃**。
另把实现名从 `.tid 文件预览` 改成 **「真 TiddlyWiki 渲染」**（en: `Rendered TiddlyWiki`）：宿主在 `candidates.length > 1` 时会画一个实现选择菜单（`rendererId` 按标签页记忆，这是它让"修好了"看起来像"没修好"的原因），名字写清楚用户才能自己切回来。
守门 `verify-tid-preview` 17 条：新增「17 位戳格式化 / 非 17 位原样」「摘要只单列 title·tags·时间且机械字段进 other」「没有 title/时间时不硬造」三条；i18n 475 → 476 键（`frame.tidMoreFields`）。

- **v0.33.2**（2026-10-26）：**`.tid` 预览仍不生效 —— 这次是"服务还没出现就放弃"**。
v0.33.1 修好了 `key` 配对，但用户实测仍是纯文本，且 devtools 里 `[class*="dsh-tw-tid"]` 数量为 0（正文组件压根没渲染）。
根因在插件的**加载顺序**：`documentPreviews` 是另一个插件（宿主的 `dsh-client-ui-sidebar-documentpreview`）用 `ctx.reflect.provide(...)` 提供的，本插件若先加载，`ctx.get(...)` 那一瞬间拿到 `undefined`，v0.32/0.33.0/0.33.1 就**静默 return** 了 —— 界面上看不出差别（宿主用内置纯文本兜底），console 里也一条日志都没有，等于把失败藏起来。
现在改成**短轮询等它出现**（250ms × 40 ≈ 10s），并给每一步补 `[dsh-tiddlywiki]` 前缀的诊断日志：`ctx.get`/`ctx.slots` 是否存在、第几次尝试注册上元数据、正文是否注册进 keyed 子槽、等不到时的 warn。正文外壳加 `data-dsh-tw-tid` 标记，devtools 里一条 `document.querySelectorAll('[data-dsh-tw-tid]').length` 就能判定我们的组件到底有没有渲染。
守门同步改判据：不再钉"查一次就返回"，改钉 `setTimeout(attempt, 250)` 的轮询、`getter('documentPreviews')` 的取值形态、以及"服务始终没出现"那条可诊断 warn —— 静默跳过从这一版起是**被测出来的**行为，不再是遗漏。

- **v0.33.1**（2026-10-26）：**`.tid` 预览改为真正生效**（v0.32.0 那一版静默失效：打开 `.tid` 仍显示纯文本）。
根因是宿主契约里我读错的一处：DSH 的文件预览分「元数据 + keyed 正文」两半，**正文按 `key` 配对** ——
宿主自己写的是 `ctx.slots.register({ name: sidebar.right.tab.document, key: BODY_ID }, Body)`，而 v0.32.0 写成了 `id:`。
**它不报错、不告警**，宿主找不到渲染器就安静地用内置纯文本兜底，于是症状看起来像「功能没做」。
同一轮照抄宿主补齐另外三个形状：`priority` 是**字符串**（宿主只判 `=== builtin ? 0 : 1`，非 builtin 才压得过内置纯文本）、`title` 传**函数**（语言切换可重取）、`wrap: false`（我们产出 HTML 而不是按行折行的纯文本）；
正文取文本也从「只认 `content.text`」改成读 `content.pages`（`loading: text-pages` 时宿主给 `{ kind: text, pages }`，每页 `{ offset, lines, text }`，按 offset 排序拼接）。
